# 赞赏弹窗

English version: [Donation Dialog](../../en/features/donation-dialog.md).

## 概述

自包含的页脚入口 + 模态弹窗（`js/donation.js` + `css/donation.css`）：在浏览器本地实时渲染支付宝 / 微信支付赞赏二维码——无静态图片、无第三方二维码服务、无统计分析。

## 背景

静态工具站通常直接贴一张赞赏二维码截图。这让仓库与二进制图片耦合、每次换收款链接都要重传图片，还会让仓库体积悄悄膨胀。本项目早期迭代还试过自制 URL 方案拉起支付 App——手机浏览器与系统对此的处理极不一致。

## 问题

从流程层面看：手机访客希望不输入就能打赏；桌面访客只需要一个可扫的码。自造 `alipays://` 方案经常无声失败（浏览器吞掉导航、系统毫无反应、页面没有任何反馈），而 `wxp://` 微信载荷在浏览器里根本无法拉起。同时组件必须能整体丢进任意静态页面，不引入依赖、构建工具或追踪脚本。

## 目标

- 一行集成：一个 `[data-donation]` 挂载点 + 脚本与样式。
- 二维码在打开瞬间于浏览器内计算——换收款链接只需改一个配置对象，不必重新生成图片。
- 各渠道在手机端行为正确：系统能拉起就真实跳转，不能就诚实地给二维码回退。
- 用前零成本：弹窗打开前不下载任何供应商脚本。
- 弹窗对键盘与读屏器完全可操作。
- 无分析统计、无支付结果追踪、无 Cookie。

## 非目标（Non-Goals）

- **支付确认或金额管理**——组件只展示收款二维码，永远不知道支付是否发生。
- **拉起微信 App**——浏览器场景下技术上不可靠；扫码是受支持的路径，这一点不会去「修」。
- **币种 / 金额选择 UI**——载荷就是支付渠道链接本身编码的内容。
- **国际支付渠道**（PayPal、Ko-fi 等）——明确不做；双渠道配置是刻意精简。
- **组件打包发布**（npm 包、ESM）——以纯文件形态交付，与宿主项目一致。

## 方案概览

`donation.js` 是一个 IIFE，除可选的 `window.PG.i18n`（存在则跟随站点语言，否则回退浏览器语言）外不依赖宿主。

- **配置：** 一个 `DONATION_CONFIG` 对象，每个渠道一条 `qrContent` 字符串——支付宝官方 `https://qr.alipay.com/…` 链接与微信 `wxp://…` 载荷。换收款渠道就是改一个对象。
- **二维码编码：** 内联的 MIT 许可
  [`qrcode-generator`](https://github.com/kazuhikoarase/qrcode-generator)
  （`js/vendor/`），**首次打开弹窗时**才以 `<script>` 注入，之后缓存在一个 Promise 里（加载失败会重置 Promise，下次打开自动重试）。
- **渲染：** 白卡片上的整数模块尺寸——纠错级别 M、4 模块静区、按约 220 px 目标推算缩放、感知 `devicePixelRatio`（上限 3×）、`#111` 深色绘于 `#fff` 白底。
- **渠道逻辑（关键设计决策）：**
  - 桌面端：两个渠道都直接渲染二维码。
  - 手机 + 支付宝：弹窗先进入「正在打开支付宝…」态、后台预渲染二维码，然后经 `window.location.href` 跳官方链接。1.3 秒计时器检查 `document.visibilityState`——页面仍可见（没有发生 App 接管）就翻到二维码回退视图。「显示二维码」按钮始终在场，失败绝不是死路，成功也绝不被误判。
  - 手机 + 微信：永远显示二维码（见非目标）。
- **DOM：** 弹窗在加载时构建一次、之后复用；标签页、画布与各状态段落以 `hidden` 切换。

## 详细行为

| 方面 | 行为 |
| --- | --- |
| 入口 | 注入 `[data-donation]` 的按钮；文案跟随站点语言 |
| 打开 | 显示遮罩、重选当前渠道、焦点移到关闭按钮；记录先前聚焦元素 |
| 关闭 | × 按钮、点击遮罩或 ESC——焦点归还给打开者 |
| 标签页 | 支付宝 / 微信；`role=tablist` + `aria-selected`；左右方向键切换渠道并移动焦点 |
| 二维码尺寸 | 按载荷自动选 QR 版本 1–40；模块 ≥3 px、卡片约 220 px |
| 加载失败 | 主体切到错误提示；重新打开会重试库加载 |
| 切换语言 | 经 `PG.i18n.onChange` 实时重刷全部弹窗文案 |
| 减少动效 | 站点样式表的 `prefers-reduced-motion` 规则生效；弹窗自身不添加任何动画 |

`test/donation-test.js` 的 13 项契约测试把上表大部分内容钉死（载荷、禁用 `alipays://`、不引用图片、键位一致、跳转规则、回退接线、无障碍钩子、懒加载、挂载契约、CSS 类覆盖）。

## 用户体验

桌面：页脚入口 → 双标签弹窗 → 白卡片二维码 → 手机扫码。手机：同一入口；支付宝标签尝试拉起 App、失败优雅回退二维码；微信直接显示二维码。

## 兼容性与历史影响

无历史行为受影响。组件在同一个初始发布内替换了更早的赞赏区块（静态二维码、方案跳转）；由于没有外部使用方，替换是彻底且终态的。对宿主的集成契约：提供 `[data-donation]`、引入 `css/donation.css`、以 `defer` 加载 `js/donation.js`、可选暴露 `PG.i18n`。

## 数据与隐私影响

- 零存储：组件不写 localStorage / Cookie。
- 网络：首次打开弹窗时加载一个同源资源（供应商编码器）——按资源计，非数据。
- 跳转：手机端支付宝跳转官方收款链接（见[隐私说明](../privacy.md)）。
- 无分析事件、无支付结果回调。

## 性能影响

首次打开前组件只占一个小脚本标签的内存；供应商编码器（未压缩约 20 KB）仅在首次打开时加载，固定载荷的二维码是几毫秒级的画布绘制。除此之外不作量化声明。

## 当前局限

- 在拦截一切跨应用导航的手机浏览器上，支付宝标签页总会落到回退二维码——计时器无法确定区分「被拦截」与「App 已打开」；显式按钮覆盖了这种情况。
- 微信在所有平台都是扫码（刻意为之，见非目标）。
- 弹窗的白底二维码卡片假设浅色背景；深色主题的宿主可能需要调整 `css/donation.css`。
